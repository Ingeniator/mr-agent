mr-agent

LLM bot for GitLab merge requests

Two scheduled GitLab CI jobs that go over open MRs labelled ai-review. One writes an AI summary into the MR description, the other posts an incremental code review checked against the repo's CLAUDE.md rules. Standard library Python only.

Add the ai-review label to an MR to opt it in to both jobs, and remove it to stop. MRs without the label are never touched. In an MR, the sidebar's Labels field or a /label ~ai-review comment both work.

The jobs

Two jobs, one set of helpers

mr-description
  • Fixed sections: What, Why, Compatibility, How to test.
  • Block sits between <!-- ai-description:start head=SHA --> and <!-- ai-description:end -->. Text outside it is kept.
  • Appended on the first run, replaced after each push. Put empty markers in the description to choose where it goes.
  • If the LLM rejects the prompt, an earlier summary stays under a failure note.
  • Re-reads the MR after the LLM call and writes only if HEAD hasn't moved.
mr-review
  • Inline comments on diff lines plus a summary note, at most MAX_FINDINGS findings sorted by severity (blocker, major, minor).
  • The prompt includes the root CLAUDE.md and the CLAUDE.md of every touched component, read from main.
  • Incremental: each run reviews only what changed since the last reviewed HEAD, including after a force-push.
  • Findings that can't be attached to a new line go into the summary.
  • Posts nothing if HEAD moved while the LLM was answering.

    mr-review

    How a follow-up review marks new lines

    The prompt always contains the MR diff (base_sha..head), because GitLab accepts inline comments only on lines of the MR diff. On a follow-up review, the diff last_reviewed..head is intersected with the MR diff: added lines are matched by line number, and removed lines by line number too, mapped from last_reviewed to the MR base through base_sha..last_reviewed. Lines that survive get * and ~. Files with nothing new are dropped from the prompt, and inline comments are allowed only on * lines.

    Where findings land
    
  
    
  
    A line the MR added earlier and has since removed is no longer in the MR diff at all, so the prompt lists such lines separately. Changes that arrived by merging or rebasing onto the target branch drop out of the intersection. When nothing else changed, the marker in the last review note moves to the new HEAD without a new note. After a force-push the old HEAD is fetched by SHA; if that fails, or no MR version had it as its HEAD, the whole MR is reviewed again.
    

    


    
  Threat model
  
    Why MR branches can't reach the tokens
    
  
    
    
    01
    Schedule only. The job's only rule is CI_PIPELINE_SOURCE == "schedule" on the default branch with LLM_MR_BOT == "1". It never runs in MR pipelines. Polling instead of a webhook trigger costs up to one schedule interval of latency; ADR-0001 explains why.
    
    
    02
    Protected variables. LLM_API_KEY and MR_BOT_TOKEN are masked and protected, so feature-branch pipelines don't receive them.
    
    
    03
    Pipeline variables locked. "Minimum role to use pipeline variables" must be Maintainer or No one. Otherwise someone could start a run on main with their own CI_API_V4_URL or GIT_CONFIG_* and send the tokens elsewhere.
    
    
    04
    MR code is data. MR commits are fetched by SHA and only diffed, never executed.
    
    
    05
    Rules come from main. CLAUDE.md files are read from the checkout of the default branch, so an MR can't rewrite the rules it's reviewed against.
    
    
    06
    Markers only from the bot. Review markers count only in notes the bot user wrote, so a quoted marker in someone else's comment can't move the review base.
    
    
    07
    No quick actions. Every description and note the bot writes gets a space in front of any line that starts with /. This stops a diff from steering the model into emitting /approve or /close, which GitLab would run as the bot.
