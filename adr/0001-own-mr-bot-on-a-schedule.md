# ADR-0001. Свой MR-бот, запуск по расписанию на `main`

- **Статус:** принято
- **Дата:** 2026-10-15
- **Область:** весь репозиторий; джобы `mr-description`, `mr-review`,
  `mr-review-stats`, `mr-bot-health` в `.gitlab-ci.yml` проекта, который ревьюят
  (`gitlab-ci.example.yml`)

## Контекст

Нужны LLM-описание и LLM-ревью MR, проверенные по правилам корневого `CLAUDE.md`
и `CLAUDE.md` затронутых компонентов, через уже работающий LLM-шлюз
(`LLM_BASE_URL`). Токены (`LLM_API_KEY`, `MR_BOT_TOKEN`) не должны попадать в
код из веток MR.

Свой бот стоит денег: около 2,3 тыс. строк скриптов, 2 тыс. строк тестов и
`overview.html` — всё это сопровождаем мы.

## Решение

1. **Свой бот** на стандартной библиотеке Python (этот репозиторий), а не
   готовый ревьюер.
2. **Опрос по расписанию**, а не вебхуки: джобы запускаются только в
   pipeline по расписанию на ветке по умолчанию, проходят по открытым MR с
   меткой `ai-review` и останавливаются после `MAX_MRS_PER_RUN` MR, дошедших до
   LLM. Токены — защищённые CI-переменные, так что код ветки MR их не видит.

## Последствия

- Пуш в MR получает описание и ревью только на следующем запуске расписания:
  до одного интервала плюс сам запуск, дольше при очереди.
- Каждый запуск идёт, даже когда ни один MR не менялся; пустой запуск стоит
  одного shallow-клона и нескольких чтений API.
- Чтобы измерять обе стороны компромисса, нужен OTLP-коллектор
  (`OTEL_EXPORTER_OTLP_ENDPOINT`). Время от пуша до ревью — атрибут
  `mr_bot.latency_s` спана MR, число MR, отложенных из-за лимита, —
  `mr_bot.deferred` спана запуска (`telemetry.py`); `mr-review-stats` их не
  считает. Без коллектора это только строки в логе джобы, и компромисс не
  измеряется.
- Сопровождение кода бота и его документации — наше.

## Рассмотрено и отклонено

### GitLab Duo Code Review

Требует Ultimate с аддоном Duo Enterprise, а на self-managed — ещё Duo
Self-Hosted со своим AI Gateway перед моделью; code review там в лучшем случае
beta. Включение — решение администраторов инстанса, а не проекта, и наш
LLM-шлюз оно не использует.

### pr-agent (Qodo, open source)

Сверено с исходниками pr-agent 0.47.0 (`main` на 2026-10-15), а не только с
документацией. Поддерживает GitLab и OpenAI-совместимый endpoint (через
litellm), то есть может ходить через наш шлюз.

**Где pr-agent не хуже или лучше:**

- *Наши правила.* `repo_context_files` принимает любые пути репозитория и
  подставляется в промпты `review`, `describe` и `improve`; по умолчанию
  (`repo_context_from_default_branch = true`) файлы читаются с ветки по
  умолчанию, не с головы MR — как у нас.
- *Без повторов.* `persistent_finding_state` (включён по умолчанию, GitLab
  поддерживается) переносит находки между полными ревью; inline-тред с
  находкой, который закрыл кто-то кроме бота, считается отклонённым.
- *Описание MR.* `describe` с `use_description_markers` пишет только между
  своими маркерами, остальной текст сохраняется — как `mr-description`.
- *Большие MR.* Diff сжимается под `max_model_tokens`, лишнее отрезается
  (`large_patch_policy = "clip"`). Наш бот отправляет diff целиком и при отказе
  LLM помечает голову как неудавшуюся до следующего пуша — MR остаётся без
  ревью.
- *Чего у нас нет вовсе.* `improve` (предложения кода с готовым патчем),
  `ask` и команды в комментариях (в режиме вебхук-сервера), контекст из
  артефактов CI (`ARTIFACT_PATH`), выбор провайдера и fallback-моделей.
- *Обкатанность.* Широко используемый проект с сообществом; наш бот новый, и
  данных о его точности (`mr-review-stats`) пока нет. Проверено ли, что он
  лучше, — неизвестно.

**Где pr-agent хуже или требует нашего кода:**

- *Модель безопасности.* Готовый режим GitLab pipeline запускается на
  `merge_request_event`, то есть в pipeline ветки MR — токены пришлось бы
  отдать коду ветки. Чтобы держать их защищёнными, нужен свой цикл: джоба по
  расписанию на `main`, выбор MR с меткой `ai-review`, пропуск уже
  обработанной головы и вызов `pr_agent.cli --pr_url=…` на каждый. Это
  меньшая, но не нулевая часть нашего кода (`for_each_open_mr`, маркеры
  «голова уже обработана», лимит на запуск, backoff).
- *Правила по затронутым компонентам.* `repo_context_files` — фиксированный
  список; каждое ревью получает все четыре `CLAUDE.md` (~700 строк) при
  лимите `repo_context_max_lines` 500 по умолчанию — лимит придётся поднять.
  Наш бот добавляет только `CLAUDE.md` затронутых компонентов.
- *Бюджет промпта.* `max_model_tokens = 32000` по умолчанию. Наши ревью уже
  доходят до ~41 тыс. токенов промпта (строка `LLM call:` в логе джобы), так
  что с настройками по умолчанию pr-agent будет резать diff там, где наш бот
  видит его целиком; лимит надо поднять под контекст модели.
- *Инкрементальное ревью.* Для GitLab оно есть (`review -i`): diff от
  последнего коммита, который старше прошлой ревью-заметки, до головы через
  compare API. Но коммиты отбираются по времени, а после rebase на целевую
  ветку в diff попадают и её изменения — наш бот их отбрасывает и после
  force-push достаёт старую голову по SHA. И главное: инкрементальный запуск
  отключает `persistent_finding_state`, так что выбирать приходится одно из
  двух — «только новое» или «без повторов». У нас есть оба сразу.
- *Измерение ревью.* Аналога `mr-review-stats` нет: ни вердиктов по
  находкам, ни точности по версии промпта. Джоба читает только треды и
  голоса GitLab и маркеры в находках; на комментарии pr-agent её можно
  перенастроить, но без маркера с версией промпта и моделью — только общую
  точность.
- *Наблюдаемость отказов.* Аналогов `mr-bot-health` (MR без ревью дольше
  `STALE_AFTER`, истекающий токен) и спанов на MR со статусом нет — они
  остались бы нашими при любом выборе.
- *Размер и зависимости.* ~50 тыс. строк Python и 30 прямых зависимостей
  (litellm, fastapi, langfuse, gunicorn, …) против стандартной библиотеки:
  нужен свой образ или зеркало пакетов во внутреннем реестре и обновления
  вслед за апстримом.

**Итог.** По возможностям pr-agent шире (`improve`, сжатие больших diff,
обкатанность), наш бот точнее подогнан под наши ограничения (запуск только
на `main`, правила по компонентам, инкрементальность вместе с подавлением
повторов, измерение). Какой из них даёт лучшие находки на наших MR, из кода
не следует — это решает только проба (см. «Открыто»). Поэтому pr-agent —
кандидат на замену `mr-review` и `mr-description`, а не отклонённая
альтернатива. При замене нашими остались бы цикл по MR, `mr-review-stats` и
`mr-bot-health`.

### Вебхук вместо расписания

Вебхук проекта на события MR может вызывать trigger API pipeline для `main`
(`/projects/:id/ref/main/trigger/pipeline?token=…`), а джоба — читать MR из
`TRIGGER_PAYLOAD`. Токены остались бы защищёнными, ведь pipeline идёт на
`main`. Не выбран, потому что:

- нужен второй секрет: вебхук несёт в URL trigger-токен, а он запускает
  pipeline на `main`;
- расписание само себя лечит: пропущенный или упавший запуск покрывает
  следующий, а потерянная доставка вебхука оставляет MR без ревью до
  следующего пуша;
- всплески разбираются в одном месте: вебхук запускал бы pipeline на `main` на
  каждое обновление MR (пуши, правки меток и заголовка), в очереди друг за
  другом по `resource_group`; запуск по расписанию смотрит все MR и
  останавливается после `MAX_MRS_PER_RUN`.

## Открыто

- **Пробный запуск pr-agent.** Прежде чем расширять бота, запустить pr-agent
  рядом с ним на нескольких MR с `ai-review`: джоба по расписанию на `main`, CLI,
  наш шлюз и та же модель, `repo_context_files` с четырьмя `CLAUDE.md`,
  `repo_context_max_lines` около 800, `max_model_tokens` под контекст модели,
  полное (не `-i`) ревью с `persistent_finding_state`. Сравнивать на одних и
  тех же головах: точность по `mr-review-stats` (перенастроенной на треды
  pr-agent), число находок, токены на ревью, MR без ревью. Если находки не
  хуже — удалить `mr_review.py` и код, нужный только ему. Оставить бота, если
  проба покажет, что правила по компонентам, инкрементальность или поведение
  после rebase важны на практике.
- **Вебхук в дополнение к расписанию.** Если задержка станет важна или лимит
  запусков будет упираться неделя за неделей, добавить вебхук рядом с
  расписанием, а не вместо него: маркеры уже делают повторный запуск пустым, а
  расписание подбирает то, что вебхук пропустит.
- **Отдельный репозиторий: бот запускается в CI каждого проекта.** Бот
  начинался в каталоге `.devops/gitlab/` одного проекта и переехал сюда, чтобы
  им пользовались и другие. Рассматривались два способа:
  - *Один бот на все проекты*, со своим проектом в GitLab и расписанием там.
    Нужен токен с доступом к чужим проектам (утечка затрагивает все сразу),
    правила читаются через API, список проектов — отдельная настройка.
  - *Бот как пакет в CI проекта, который ревьюят* (выбрано). Джобы и
    расписания остаются в проекте (`gitlab-ci.example.yml`), бот ставится в
    джобе: сейчас `git clone` по `MR_AGENT_REF`, позже — из PyPI. Решение 2
    не меняется: токены — защищённые переменные этого же проекта, правила —
    из его клона (`REPO_ROOT`, рабочий каталог джобы), коммиты — из его
    `origin` (`repo.remote()`), MR — по его `CI_PROJECT_ID`. Токена на чужие
    проекты нет.

  Единственное, что было вписано в код под первый проект, — его описание в
  промптах; теперь это `PROJECT` из `MR_AGENT_PROJECT` в CI проекта
  (`project.py`). Ключ LLM переименован в `LLM_API_KEY`: проекты, которые
  запускали бота из своего каталога, при переходе переименовывают переменную.

  Остаётся открытым:
  - *Какие файлы считаются правилами.* Сейчас корневой `CLAUDE.md` и
    `CLAUDE.md` каждого верхнего каталога, который трогает MR, — соглашение
    первого проекта. Обобщать, когда появится проект с другим.
  - *Автор заметок бота.* Свои заметки бот узнаёт по автору
    (`bot_user_id()`). Новый токен — новый бот-пользователь: все MR
    ревьюятся заново, а `mr-review-stats` теряет прежние находки. При
    переходе проекта со своей копии на пакет токен оставлять прежним.
  - *Маркеры* (`markers.py`) — общее состояние со всеми версиями бота, что
    стоят в проектах. Их формат меняется только expand/contract.
  - *Один бот на все проекты* — если понадобится, это новый ADR (токен на
    чужие проекты, откуда правила).
